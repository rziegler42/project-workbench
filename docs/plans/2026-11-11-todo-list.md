# Build the todo list, stage 1: the `todo` command, the policy and the plan-close clause

Status: Completed
Created: 2026-11-11
Candidate: none (work the owner asked for on 2026-11-11 with an approved design; no roadmap candidate names it, and the owner decides whether one is added)
Specs: todo-list, groundwork, code-work, module-contract, knowledge-tools, command-permissions

## Goal

After this plan the owner has a personal, per-clone todo list that agents can add to and drop from, and that the owner can read when asking what to do next. It is the stage 1 of `docs/specs/todo-list.md`, which the owner approved as a design on 2026-11-11.

- `groundwork` provides the capability `todo` and ships the helper `todo` with four agent-run arguments: `add`, `list`, `show` and `drop`. Items are files in the untracked `.workbench/local/todo/`.
- The `groundwork` policy block tells agents when to add an item and how to drop one. The `code-work` plan-close step adds a finished plan's deferred items, written against the capability and not against a module.
- The specs say what is built. The owner has released the package, upgraded this repository, and added the first entries by hand-run.

Not part of stage 1, and not built here: the close-out audit, a `Todo:` commit trailer, capture from rejected review findings, and a `delegated` level for any of the four keys (`todo-list.md`, "Non-goals" and "Commands").

## Scope

- `packages/workbench/groundwork/`: `module.json` (the capability, the `todo` command, the helper), the new `helper/todo`, the policy block, the tests.
- `packages/workbench/code-work/`: the `run-increment` skill's plan-close text and its test.
- Specs: `todo-list.md` (the invocation form, and its status when built), `groundwork.md`, `code-work.md`, `knowledge-tools.md` or `module-contract.md` (wherever the core capability names are listed), `command-permissions.md` (the four keys).

## Non-goals

- The items of the list: this plan adds none except the first two in increment F.
- Any change to the installer (`workbench/*.py`), the kit (`wbkit`), the `mempalace` helpers, the edit gate or the command gate.
- A change to the plan template or the `draft-plan` skill. Plans keep their own Deferred work, because nothing tracked may point at the list.
- The seeding of the list from the old plans. It is a session with the owner after increment F, not an increment.
- Any palace, tracked-file or outside-the-project store.

## Assumptions and constraints

- **Departure from the spec text (my call; the owner approves it by approving this plan).** `todo-list.md` writes the commands as `wb run groundwork todo <subcommand>`. The registry gives each `wb run <command> <argument>` its own key and level (`command-permissions.md`), and the `groundwork` command entry already holds the owner-run `accept` of the decision helper. To give `add`, `list`, `show` and `drop` their own keys without touching that pinned helper, the helper is a separate command entry named `todo`, and the form is `wb run todo <argument>`. Increment A corrects the spec in the same commit. The command is therefore named `todo` and the capability is also `todo`, so the plan-close call is `wb run --provides todo todo add ...`: the first `todo` is the capability that must be provided, the second the declared command (`module-boundary.md`: `wb run [--provides <capability>] <command> [<argument> ...]`). The spec's present `groundwork todo` form is replaced, not kept beside it.
- The helper is a single-file Python helper started by the launcher from a private copy, as `helper/groundwork` and `helper/doccheck` are, and reads and writes through the kit (`wbkit.safefs`), which follows no link, reads regular files with one link, and replaces files through a temporary name. [source: `helper/groundwork`, `module-boundary.md`]
- The credential rules are a copy of `CREDENTIAL_PATTERNS` and the scan of the `mempalace-notes` helper, not a move into the kit and not an import across modules, because a module's helper may not import another module's code and a kit change is a wider risk than this plan needs (my call). A test in the new module pins that the pattern names and expressions equal those of the `mempalace-notes` helper, so a drift fails a test (increment A). The spec asked the plan to name the copy or say why a second is needed; this is the second, and the reason.
- Nothing runs through `wb run todo` until the owner has released the package and upgraded this repository (increment F). Increments A to E test the helper directly, as the other helpers' tests do.
- A change under `packages/` is shipped through `release-approvals`, which is the owner's. The edit gate watches only the file-writing tools and the command gate keeps its present levels; this plan changes neither. [source: `todo-list.md`, "What is left to the builder", the evidence note]
- The new keys are `wb run todo add`, `list`, `show` and `drop`. All are agent-run and offer `block` and `none` with the default `none`; none is owner-run and none declares `delegated`. [source: `todo-list.md`, "Commands"; `command-permissions.md`]
- Every number below (120, 200 and 200 characters; 4 KiB; 5 KiB) comes from `todo-list.md`, "An item".

## Completion criteria

1. `wb run todo add --title '<title>'` writes one item file in `.workbench/local/todo/` and prints its ID; a repeated title is refused; a bound or a credential-shaped string in any field is refused without echoing it.
2. `wb run todo list` prints every item oldest first with its age, honours `--size`, `--mechanical` and `--older-than`, lists an unreadable file as unreadable, and prints no field that matches a credential rule.
3. `wb run todo show <id>` prints one item in full under the same scan; `wb run todo drop <id>` removes the file, prints the item and appends one line to the drop log.
4. `wb verify packages/workbench` reports no problem; `groundwork` provides `todo`; the helper's tests, the `groundwork` tests and the `code-work` tests pass; the test that pins the copied rules passes.
5. The `groundwork` policy block carries the capture and drop rules and names no other module; the `run-increment` skill carries the plan-close clause "where a module provides `todo`", and `code-work` gains no `requires`.
6. The specs say what is built, and the stale line of `groundwork.md` about "no helper that an agent runs" is corrected.
7. After the owner's release and upgrade, the four commands run through `wb run` in this repository, and the first two entries are on the list. The result records what was and was not seen in use.
