# graphify

Status: Draft. Written 2026-11-09 for the roadmap candidate `workbench-v1#graphify-module`, which the owner chose to begin on that date. Nothing in it is built. The calls marked **(my call)** are the author's and are not the owner's until the owner approves this spec. The owner answered the six open questions of the first draft on the same day; "Decisions of the owner and what is still open" records each answer.

Terms are defined in `terms.md`. The declaration it must satisfy is defined in `module-contract.md`; the launcher, the kit and module commands in `module-boundary.md`; the authority rules in `trust-and-approval.md`. Its place among the knowledge modules is in `knowledge-tools.md`; its sibling `mempalace` is specified in `mempalace.md` and is the model for the module's shape, not a dependency.

## Scope

`graphify` is a first-party module of type `module` that lets an agent in a workbench project ask questions of **structure and impact** about the project's code: what calls what, what imports what, what would be touched by a change to a function or a file. It is a front end for the owner's `graphify` program (installed with `uv`; the program's package is named `graphifyy`), which parses source files into a graph and answers queries over it. The module holds no graph of its own and calls no language model.

The earlier `graphify` systems of the owner (the template module in `claude_project_template` and the global commands of `claude_global_config`) are lessons learned and not a source of truth ("Evidence", below). The module is designed afresh, against what they got wrong.

| field | value |
|---|---|
| type | `module` |
| provides | `code-graph` |
| requires | nothing |
| helpers | `graphify` (the vendor program, expected on `PATH`; a missing one is a warning at install) and the module's own helper `helper/graphify`, which wraps it |
| fills | `policy` (a short block). No other slot: the contract has base-owned slots (`policy`, `docs-index`) and slots a module owns, and none exists for `.gitignore` |
| writes | nothing declared. The graph is the helper's runtime output, outside the project, in `~/.local/share/project-workbench/graphify/<project id>/` ("The module contract and where the graph is written"). A `.graphifyignore` at the project root is a candidate `writes` entry; see "The graph and what it indexes" |
| ships | `helper/graphify` and one neutral skill, `use-code-graph`, and the policy block |
| commands | `graphify`, runtime `python`, kit 1; arguments `status`, `query`, `path`, `explain`, `affected`, `hubs`, `update`; none is owner-run |

It is run as `wb run graphify status`, `wb run graphify affected ...` and the like by an agent. There is no semantic extraction, no hook installation and no platform installer in it (see "Non-goals").

**What the module is for, in one sentence (my call):** to answer "who depends on this?" and "what does this touch?" from the code's own structure, with an honest statement of how current the answer is and what the graph cannot see, and nothing more.

## Non-goals

- **A semantic layer (my call, and the main change from the earlier systems).** The module does not run, schedule, refresh or depend on the vendor program's language-model extraction (`extract`, document and image ingestion, `--mode deep`, community naming, `label`). The earlier systems' semantic layer was out of date whenever it was queried and was therefore seldom used (the owner's account, confirmed by the plan notes in "Evidence"). The module's graph is **structural**: derived from source by the program's local parser, with no key, no network and no model. The module works only with a graph that holds the structural layer alone. If the output folder holds a graph with non-structural nodes (the owner built a semantic layer by hand with the program in a terminal, or ran another of its commands there), the module calls it `foreign` (see `status`), answers nothing from it, and `update` refuses to write over it; the owner moves or deletes the folder, and the module builds a new one. It never mixes a layer it does not maintain into an answer, and never deletes one.
- **A gate or a receipt.** No plan carries a graph receipt, no plan template asks for one, and no step of any module requires a query. The discovery gate was dropped on 2026-10-19 (`code-work.md`, "no discovery gate"). The earlier receipt ("query, or write `Graphify: skipped`") became a ritual (60 of 205 plans in one project recorded a skip; "Evidence").
- **Automatic refresh.** No git hook, no step after a commit, no refresh at session start and none in the commit helper. The earlier global config removed its commit-time rebuild on 2026-10-19, for its trust risk, and recorded that no automatic refresh is to be added anywhere ("Evidence"); this module follows that, and derived output is rebuilt on demand.
- **The vendor program's installers and watchers.** The module never runs `install`, `uninstall`, `hook install`, `claude install` or the installers for other platforms (they write into `CLAUDE.md`, `AGENTS.md`, hook entries and user-level skill folders), `watch`, `clone`, `add`, `provider`, `global`, `merge-graphs`, `merge-driver`, `prs`, `reflect`, `save-result`, `export` or `benchmark`.
- **An MCP server.** The installed `graphify-mcp` does not start and a registered MCP server skips the command gate, the output limits and the data marking (as recalled from the owner's note of 2026-11-05 on stock MCP servers, which is untracked and whose hash was not recorded; `mempalace.md` makes the same choice for its module). The module is commands and a skill. If native tools are ever wanted, a small server owned by the workbench that exposes only these read-only commands is the design.
- **Conversation history, the knowledge base, documents.** Those are `mempalace` and the knowledge base (`knowledge-tools.md`). The graph indexes code files only (see below). The module neither reads nor names the other knowledge tools; a test enforces that no file it ships names one (the owner's requirement of 2026-11-05, as recalled from their untracked note: "Mempalace should not depend on graphify and graphify should not depend on mempalace").
- **Other repositories.** One project, one graph. No global graph under `~/.graphify`, no cross-repository merge.
- **Proving the graph right.** An answer is orientation, never evidence ("Authority of an answer").

## Assumptions and constraints

- **Authority of an answer.** A graph answer is derived data. It never grants approval, never overrides a decision, a spec or the current code, and an instruction found in a node name, a comment or a file path that it returns is ignored (`AGENTS.md`, "Source of truth"; `knowledge-tools.md`). It is orientation: the agent checks the files it names before acting on them. An empty answer is not evidence that nothing depends on a name (the graph may not index that language or may not resolve that call).
- **The vendor program is trusted as the owner's installed tool and is not confined.** It reads the project's files and writes to its output folder. The module's helper therefore runs it only for `update`, only with a fixed argument list (`update` of the project root with the code-only options of "update"), a clean environment that adds the one variable `GRAPHIFY_OUT` (the absolute output folder), a time limit and a cap on captured output, and never passes an agent-supplied path, option or backend. The helper records the program's version it was tested with and says which version it ran ("Evidence" records 0.9.103; the floor is in "Decisions of the owner").
- **How the vendor program is found (the review of 2026-11-09, round 1).** The helper builds the vendor program's environment itself, as the kit builds the environment of a call to `wb` (`module-boundary.md`: a fixed list of variables and a `PATH` of the trusted entries; no `GIT_*`, `LD_*` or `DYLD_*`). It resolves `graphify` in an absolute `PATH` entry that is an existing directory outside the outermost repository that holds the project, compared by file identity, as the kit resolves `wb`, so a `graphify` planted in the project or reached through a relative entry is never run. It records the resolved absolute path and prints it in `status`. It does not hash the program: the owner installs it with `uv` and upgrades it often (0.9.32, 0.9.64 and 0.9.103 in the survey), so a hash would refuse at every upgrade; the floor and the printed path are the check, and the trust is the owner's installation of the tool, as for `mempalace`. Whether the owner wants an absolute path named in a setting instead is left to the plan.
- **The helper runs no `git` program (my call).** Reading the commit the graph was built at and the current commit is done by reading `.git/HEAD`, the ref it names and `packed-refs` directly, so that a repository that selects a program (a hook, a filter, a configured command) cannot make `status` run one. The earlier systems needed a 1,000-line wrapper for the trust questions of calling the vendor program and git; this module keeps the surface small by calling the vendor program in one place and git nowhere.
- **The module contract and where the graph is written (the review of 2026-11-09, round 1).** `module-contract.md` says "All writes stay inside the project, and a module's own writes stay inside its own namespace" and lists what a module may write: its namespace `.workbench/<package>/<module>/`, the slots in `fills`, and the paths in `writes`. That text governs the files the installer writes from a declaration. It does not say where a helper's runtime output goes, and the repository already has a helper that writes outside the project: `mempalace-notes` writes under `~/.local/share/project-workbench/mempalace` (`mempalace-notes.md`), and `mempalace` files into a palace the owner's program keeps outside it. The draft treats the graph the same way: a runtime output folder owned by the helper, declared nowhere in `writes`. `.workbench/local/` has no such precedent and is not in a module's namespace, so a module that wrote there at run time would be writing where the contract names no owner. **Two consequences for the plan:** its first module increment checks whether the contract's sentence needs a one-line clarification that a helper's runtime data may live under the account's data directory (a change to a spec that the owner approves, not made here), and the owner's choice between the two locations stays open (decision 2), the data directory being the draft's default for these reasons.
- **The graph lives outside the project, in `~/.local/share/project-workbench/graphify/<project id>/` (my call, after the owner's question of 2026-11-09 whether it could live in `.workbench/local` or in `~/.local/share/project-workbench/`).** Both can: the program honours the environment variable `GRAPHIFY_OUT`, which names the output folder as an absolute path, and the helper sets it for every run (tested 2026-11-09 on a two-file scratch project: with it set, `update` wrote `graph.json`, `graph.html`, `GRAPH_REPORT.md`, `manifest.json` and `cache/` to the named folder and nothing into the project; `affected` answered from it with `--graph`). I take the data folder rather than `.workbench/local` because the graph is derived, large (the larger earlier graph was 26.9 MB), per clone, and best kept where the agent's file tools cannot write it and no tracked-tree tool (`git`, a search, the program itself) walks it. `.workbench/local` would also work (it is untracked and inside the project) and is the alternative if the owner prefers the graph to go with the clone. The project id is the one the installer already keys its guarded store by. The helper still treats `graph.json` as data it validates (size cap, parse limits, expected keys) and never trusts a path or a command found in it. The `.gitignore` slot for `/graphify-out/` stays only as a guard for a run of the program by hand in the project, which would write there.
- **Everything in the output folder is untrusted input (the review of 2026-11-09, rounds 2 and 4).** `graph.json`, `manifest.json`, `.graphify_build_state.json` and the helper's own `inventory.json` (the folder is writable by anything the owner runs, so the helper trusts none of it) are read with the kit's strict, bounded JSON reader and no-follow file reader: a size cap per file (my call: 64 MiB for `graph.json`, 16 MiB for the manifest and for `inventory.json`, 64 KiB for the build state), a depth and an entry cap (50,000 entries in the manifest and in the inventory), duplicate keys refused, and a schema check. A manifest key and an inventory entry must each be a relative path without a `..` segment, an empty segment, a backslash, a colon or a NUL, and each manifest record must hold a number `mtime` and text hashes; the inventory must be an object with a format number and a list of such paths; a build state must hold the expected types. A file that fails any check makes the state `unreadable` with the one-line reason, and no field of any of them is ever used to open a file or build a path: freshness compares the manifest's keys with the helper's own inventory as strings, and stats only paths the helper found itself. A value from these files that reaches the output (a node label, a path) is printed inside the data markers, cleaned to printable ASCII and cut.
- **Every invocation of the program is captured with bounds, not only `update` (the review of 2026-11-09, round 4).** The helper starts the program with no shell, standard input closed, and reads standard output and standard error separately, each to a cap and under a time limit, whatever the command: `--version` 1 KiB and 10 seconds; `update` 1 MiB each and 300 seconds; `query`, `path`, `explain`, `affected` and `god-nodes` 256 KiB each and 60 seconds (my call; the program is given a token budget of at most 8,000, about 32 KiB, so a larger answer means the program ignored it). A stream that passes its cap, or a run that passes its limit, is stopped with its process group killed, and the command fails with the one-line state `the program's output exceeded the limit` or `the program timed out`, naming the command and the limit; it never prints a cut-off answer as if it were whole. What is read is cleaned to printable ASCII before it is shown, and standard error is shown only as a bounded diagnostic line, never mixed into the answer.
- **Output is bounded and marked.** Every query prints, before the program's text, a header line that states the graph's state (see `status`), then the answer between markers that say it is derived data, with the token budget the program was given and whether the answer was cut. The earlier systems let a 20,000-node graph answer through a 2,000-token budget and truncate without saying where.
- **Nothing tracked points to anything untracked.** The spec cites the earlier systems by name and by what a read-only survey of them found on 2026-11-09, not by path (`AGENTS.md`).
- **Tests use a fake `graphify`** that records its arguments and prints fixed text or fixed `graph.json` files; a real call to the program is made only in the plan's evaluation increment and in a hand run, as for `mempalace`.
- Standard library only for the helper. The installer's kit supplies the launcher, limits and data marking.

## Behavior

### The graph and what it indexes

- **One structural graph per project (my call).** `graph.json` in the output folder above, built from code files by the program's local parser (`update`, no model, no key). Two separate fields carry provenance, as seen in the scratch graph of 2026-11-09 and in the two surveyed graphs. **`_origin`**, on every node and every edge, is the layer: the text `ast` for what the local parser produced. **`confidence`**, on edges only, is how sure the program is of that edge (`EXTRACTED`, `INFERRED` or `AMBIGUOUS`, with a `confidence_score`) and is independent of the layer: the scratch graph's edges were all `ast` and `EXTRACTED`, and the surveyed graphs held edges of both `EXTRACTED` and `INFERRED` confidence (the survey did not say which layer the inferred ones belonged to, so the module treats the two fields as independent and tests an `ast` edge of each confidence). The rule is exact: a node or edge is structural when its `_origin` is the text `ast` and in no other case; a missing `_origin`, a null, a number, another text, or a value that is not text makes it non-structural, and one non-structural node or edge makes the graph `foreign`. `confidence` plays no part in that classification; `layers` shows the counts of each confidence beside the counts of each origin, so an agent can see how much of an answer is inferred.
- **A seeded `.graphifyignore` (my call).** The module seeds, if absent, a file that excludes what is not the project's own structure: the installer's own copies of every module (`.workbench/`), the program's output (`graphify-out/`), the review engine's state, and dependency and build directories common to the languages the owner uses. The earlier systems excluded the working plan because it changed while the graph was queried; code-only indexing makes that moot. A project edits the file freely; the module never overwrites it.
- **What is not indexed is said, not hidden.** The program's parser covers a set of languages; others are skipped silently. One of the owner's projects is Verilog, which the earlier graph did not resolve (three plans there recorded "No affected nodes found" and one that the graph "does not resolve Verilog instance" relationships; "Evidence"). `status` therefore prints a **coverage** line: for each file extension that has files in the project, how many of them are in the graph, and which extensions have none at all. A question about a part of the project the coverage line says is not indexed is not answered by the graph.

### The commands

All commands are read-only on the project: `update` writes only to the output folder, and the others read its `graph.json` and run the program's query commands with `--graph` fixed to it and `GRAPHIFY_OUT` set. The agent cannot pass `--graph`, a project path or any option the module does not list.

**`status`** (agent-safe). One block, no model, no program run (it reads `graph.json`, the program's manifest and the git refs, and lists the project's files):
- `state`: `current`, `stale`, `missing`, `unreadable`, `foreign`.
  - `current` means all of these hold: the graph's `built_at_commit` equals the current commit (when the project is a git repository and the graph records one); no file in the graph's manifest has a modification time or content hash different from the manifest's record; and **the project's inventory of source files now equals the inventory taken at the last `update`** (below).
  - **The inventory is taken by one walker, at `update` and again at `status`, and the two are compared (the review of 2026-11-09, round 3).** The helper does not try to reproduce the program's ignore rules, which it cannot see whole. It walks the project (at most 50,000 files; it never enters `.git` or the output folder) and keeps the relative paths of the files whose extension is one the program's parser covers (read from the graph's own file types and from a list the helper carries and tests). The walker applies only the exclusions it can read with certainty, under a grammar fixed here: it reads the project's root `.graphifyignore` and root `.gitignore`, and skips a directory or file only for a line that is a plain name, a `name/` directory, a leading-`/` anchored path, or a glob of `*`, `?` and `**`, with `#` comments, blank lines, `!` negation and last-match-wins as in `gitignore`. Any other syntax (a character class, an escape, a trailing-space rule, a nested ignore file, `.git/info/exclude`, a global excludes file) is **not** read as an exclusion, so the walker keeps at least every file the program keeps and never fewer: it can only over-count. `update` stores the inventory it saw in a file of the module's own in the output folder (`inventory.json`, written by the helper after the program succeeds, under the caps above). `status` walks again and compares the two as sets of strings. A file that is new, deleted or moved since the update makes the state `stale`, whatever the program did or did not index, so a file the helper's walker and the program treat differently cannot make a changed project look `current` or an unchanged one look `stale` for ever. As a cross-check, a path in the program's manifest that the walker did not list is reported as `inventory disagrees with the program` and makes the state `stale` (the walker excluded something the program indexed). When there is no `inventory.json` (a graph the helper did not make) the state is `foreign`.
  - `stale` gives the commit distance (when there is one) and the numbers of changed, new and missing source files, so the agent can see whether an `update` will matter.
  - `missing` means there is no graph. `unreadable` means it does not parse within the caps. A walk that reaches the file cap makes the state `stale` with the reason "the inventory is too large to compare".
- `layers`: node and edge counts by origin. Any node **or edge** whose `_origin` is not `ast` makes the state `foreign`: `status` shows the counts and the line `this graph holds nodes this module did not build; move or delete the output folder, then run update`. The query commands refuse a `foreign` graph with the same line, and `update` refuses to write into it. (The question of a maintained semantic layer is decision 4; the evaluation reads the old two-layer graphs outside the module, where this rule does not apply.) What the program's own `update` does to semantic nodes already in a graph was not tested and is why the module never writes over one.
- `coverage`: as above.
- `program`: the resolved path of the vendor program and its version. The version is read from the graph (`graph.graphify_version`, recorded by the program when it wrote `graph.json`; `0.9.103` in the scratch test) without running the program, and shown as the version that built the graph. When there is no graph it is `unknown (no graph yet)`; `update` and `wb doctor` run the program and report the installed version. A warning is printed when the version that built the graph is below the floor or differs from the tested one.
- `size`: nodes, edges, bytes, and a warning above a cap (my call: 10,000 nodes) that queries on a graph this large are likely to be truncated; the earlier larger graph held 19,799 nodes.

**`query "<question>" [--budget N] [--depth N] [--dfs]`**, **`path "A" "B"`**, **`explain "X"`**, **`affected "X" [--depth N]`**, **`hubs [--top N]`** (agent-safe). Each runs the corresponding program command (`query`, `path`, `explain`, `affected`, `god-nodes`) against the fixed graph, with the budget and depth capped (budget default 2,000, ceiling 8,000 tokens; depth ceiling 4; `hubs` top ceiling 30), the question or name at most 500 characters, taken as one argument and never as an option. The reply is: the header line (`state`, `built at`, `commit`, `layers`), the answer between data markers, and a last line that says whether the answer was cut and how to narrow it. The program's exit codes are read: 0 an answer, 3 an ambiguous name (the candidates are returned, so the agent can choose one), 4 no node matches (returned as "no match", with the reminder that this is not evidence of absence).
- **A stale or missing graph is not refused and not silently used.** The header says `stale` with the numbers; the skill tells the agent to run `update` first, which takes seconds. A query never refreshes: the read commands stay read-only.
- **`affected` is the impact question** and the reason for the module. It is reverse traversal over `calls`, `imports`, `references` and the like to a bounded depth. The answer lists the nodes with their files and locations and the relation that reaches them, so the agent can open the files.

**`update`** (agent-run, default level `none`, decided by the owner on 2026-11-09). Rebuilds the structural graph: `graphify update .` with the code-only behaviour and without `--force`, run from the project root with a clean environment that sets `GRAPHIFY_OUT`, the vendor output captured (at most 1 MiB) and a time limit (my call: 300 seconds). It writes only to the output folder (tested: with `GRAPHIFY_OUT` set the program wrote nothing into the project). It refuses when the vendor program is missing, when the project root is a directory the module does not recognise, when the output folder or a parent inside the data directory is a link or is not owned by the account, and when another `update` holds the lock. When the program succeeds the helper writes `inventory.json` (its own walk of the source files, see `status`) into the output folder, and then prints `status`. It never runs the program's `extract`, `cluster-only`, `label` or any model-backed command. **The version floor is enforced here and in every command that starts the program (the review of 2026-11-09, round 2):** before any other invocation the helper runs the resolved program once with `--version` (fixed argument, the clean environment, 10 seconds, output at most 1 KiB) and refuses, running nothing else, when the version is below the floor, cannot be parsed, or the program does not answer; the refusal is one line that names the resolved path, the version seen and the floor. A version above the tested one is a warning and the command runs. `status` does not start the program and so reports the version that built the graph, with a warning when it is below the floor. The program can refuse to overwrite a graph that has fewer nodes after a refactor that deleted code; the helper reports that refusal and does not retry with `--force` (the owner runs that in a terminal if they mean it).

### The skill and the policy block

`use-code-graph` is a short neutral skill (my call on its content, which the plan writes and the owner reviews):
- Use the graph when the question is **structural or about impact** and the scope is not already small and known: "who calls this?", "what imports this module?", "what else changes if I change this signature?", "where is the centre of this unfamiliar code?". Do not use it for a narrow change whose files are already named, for text search (that is `grep`), or for why a decision was made (that is the decisions and the history).
- Check `status` first when the answer matters. If it is `stale`, run `update` (seconds, offline) and ask again; do not reason from a stale graph.
- Read the coverage line before trusting an empty answer.
- Verify every file the answer names by opening it. The graph says where to look.
- Never build or refresh a graph at session start, and never as a ceremony before a plan. There is no receipt to write.

The policy block says the same in four lines and names no other knowledge tool.

### What the earlier systems taught, and how this design answers each (my calls, for the owner to correct)

| What went wrong | What this design does |
|---|---|
| The semantic layer went stale whenever any document changed, and refreshing it needed a seven-step manual procedure with parallel model workers. | There is no semantic layer. The structural layer is rebuilt in seconds with no model, so staleness is a cheap fix and not a permanent state. |
| Freshness had six states and `stale_semantic` persisted across later commits. | Four states, one of them cheap to cure; semantic content is never part of `current`. |
| A mandatory query-or-skip receipt made the graph a ritual. | No gate, no receipt, no plan template change. The skill says when it is worth a query. |
| About 1,000 lines of wrapper hardened the vendor CLI and git. | One narrow call (`update`), no git program, bounded output, no agent-supplied path or option. |
| A 19,799-node graph answered through a 2,000-token budget, truncated without saying so. | A size warning, a stated budget and an explicit "cut" line; `affected` and `path` give narrow answers. |
| A language the parser did not cover (Verilog) gave "No affected nodes found". | The coverage line states what is not indexed; the skill says an empty answer is not absence. |
| The graph was rarely consulted; plans say scope came from `grep`. | The evaluation below decides whether the module is worth building at all. |

## Evaluation before the module is built (decided by the owner on 2026-11-09: yes)

The owner was "never happy with how little graphify actually helped", and the roadmap says whether the module is built at all is the owner's choice. The owner has decided that the module is gated on evidence: no installer, helper or skill is written until the first increment of the plan has done the following and the owner has seen the result.

1. **A question set from real work.** Take 20 impact or structure questions from the plans and commits of the owner's `m65c02` and `m65c02risc` projects and of this one: for each, the change that was actually made (the files it touched) is the ground truth. Examples are "what else had to change when X changed?". The owner reviews and corrects the set, as they reviewed the action-review test set.
2. **Run the vendor program's structural graph against them** (built with `update` on the project at the commit before the change) and record, for each question, whether `affected`, `path` or `query` named the files that were in fact touched, how many it named that were not (noise), and what `grep` alone gave, on a scratch copy of each project. Nothing is run in the owner's projects.
3. **A check on the semantic layer (question 4).** `m65c02` and `m65c02risc` still hold graphs with both layers (nodes with origin `ast` and nodes with none). For each question, record whether any node of the non-structural layer named a file that was touched by the real change and that the structural layer did not name. This reads the existing graphs and builds nothing.
4. **The bound is the owner's.** The report prints the hit rate and the noise per question and per project and per language; the owner says whether it is worth building. If it is not, the candidate is closed with the evidence and nothing is built. The author's expectation, stated as a guess, is that the structural layer helps for impact questions in the languages the parser covers and not for the Verilog work.

## Acceptance criteria

1. The evaluation above has been run and reported, and the owner has said the module is worth building, before any file of the module is written.
2. The module declaration passes `wb verify` (`module-contract.md`): type `module`, provides `code-graph`, helper `graphify`, the policy slot, no other slot and no `writes` outside what the contract allows, one command with the listed arguments, none owner-run; the helper is pinned by the installer on install and compared by `wb verify`.
3. With a fake `graphify` on the `PATH`: `status` reports `missing`, `current`, `stale` (by commit and by a newer indexed file) and `unreadable`, reads the commit without starting `git` (a test installs a `git` that records and fails if called), and prints the coverage line including an extension with no indexed file, the layer counts including an origin that is not structural, and the version taken from `graph.graphify_version` (and `unknown` when there is no graph); a test adds a source file without changing any indexed file, deletes one, and moves one, and each makes the state `stale` with the right counts; a file excluded by a line the walker does not read (a character class, a nested ignore file) is counted by the walker at `update` and at `status` and so does not make the state `stale`; a path in the manifest that the walker did not list makes it `stale` with the stated reason; a graph with no `inventory.json` is `foreign`; a project over the file cap gets `stale` with the stated reason.
4. Each query command passes only the options listed, fixes `--graph`, caps the budget, depth and name, takes the question as one argument, never as an option, returns the header and the cut line, maps the program's exit codes 3 and 4, and refuses a missing program, a missing graph (with the one-line instruction) and an oversized or malformed `graph.json`; a node name or file path that looks like an instruction comes back inside the data markers and is not acted on.
