# Clone enrollment

Status: Draft. Written on 2026-11-15 from a conversation with the owner, for the roadmap candidate `workbench-v1#enrol-a-clone`. The command is built (see "As built"). It is `Current` only when the owner says so, after the owner's run on a second machine.

Each statement carries one of three marks, so that the owner can see what is theirs:

- **[agreed]** The owner said it, or approved it in a playback on 2026-11-15. It is the working position and it can still change.
- **[call]** The assistant's choice, made so the design is complete. The owner has not decided it.
- **[open]** Not decided. The builder asks the owner, or the owner decides when approving.

Terms are defined in `terms.md`. The commands this one sits beside are in `installer-interface.md`, the store and the baselines in `trust-and-approval.md` ("Acknowledgement"), and the per-clone files in `repository-boundary.md`.

## Scope

A command that makes a clone of an already installed project known on a machine that has never held it, so that the checks, `attach`, `upgrade`, `add` and `acknowledge` work on that clone. [agreed] The project's helpers are pinned afterwards by `upgrade` with a package, not by this command (decision `2026-11-15-enroll-writes-no-pins-and-leaves-them-to-upgrade-from-a-package`). [agreed]

The commands are `wb enroll` and a read-only `wb preview enroll`. [call] They are run through the `wb` launcher, never as `python3 -m workbench`, which would put the clone's own directory first on the module search path (`installer-interface.md`, the launcher rule). [call] The launcher is written by the first run of the workbench in the clone, which is the first step of the setup page `INSTALL.md`; `enroll` is a later step. [call]

## Non-goals

- Moving or copying a project to another path on one machine, or any use of an earlier project's baselines or pins (`repository-boundary.md` says such a project is treated as new). [agreed]
- Comparing the clone with the first machine's store, or with a remote. The basis of trust is the committed manifest's hashes and the digest the owner confirms. [agreed]
- Writing an approval or a pin, reading an approval record, fetching a package, or attaching a harness. The pins come from `upgrade` with a package, which verifies the package against the approvals and the bytes it would write; `approve` and `attach` stay the existing commands, run before or after as each needs. [agreed]
- Copying the owner's personal settings, review profiles or bridge endpoints. They are per machine, and `INSTALL.md` says so. [call]
- Any change to what a baseline or a pin means, or to the file formats of the store. [agreed]
- A way to enroll a project that was never installed. `install` and `adopt` do that. [call]

## Assumptions and constraints

- Every command that acts on an installed project first requires that the guarded store hold `projects/<id>/baselines` and a `seen` record equal to the clone's resolved path; otherwise the project is "treated as new here" and the command refuses. `enroll` is the one exception: it is the command that makes the project known. Source: `acknowledgement.check_known`, called by `attach`, `upgrade` and `acknowledge`; `trust-and-approval.md`, "What a command checks before it acts on a project".
- Today only `install` and `adopt` create the baselines, the `seen` record and the pins (`installplan.py`, the `store_writes` and `pinplan` steps; `upgrade` and `acknowledge` rewrite the baselines of a project already known, and `upgrade` creates the pin of a helper that has none, `upgradeplan._pins`), and `adopt` refuses an existing project ("use wb upgrade or wb add"). So a clone of an installed project cannot be made known by any command. Evidence, 2026-11-15, at commit `459dde9`: on a fresh clone with a scratch `HOME`, `preview attach` refused with "this machine holds no acknowledgement baselines for the project; it is treated as new here"; on the owner's second machine, `preview acknowledge` refused the same way and `preview adopt --dir . --package packages/workbench --select <the ten modules of the manifest>` refused with "the target is an existing project; use wb upgrade or wb add".
- The project's identity is the id derived from the manifest's seed (`manifest.project_id`), so the clone has the same id on every machine. The `seen` record holds an absolute path, so it differs between machines. Source: `acknowledgement.read_seen`, `check_known`.
- The baselines file is strict JSON, `{"baselines": {<path relative to the project root>: <sha256 hex of the bytes>}, "format": 1}`. Source: `trust-and-approval.md`, "Baselines file".
- An owner-run command is terminal-only unless its key offers `ask` or `none`; `wb rerender` offers `block` only. Source: `levels.py`, decision `2026-10-27-rerender-is-terminal-only`.
- A tracked document does not cite an untracked file. Source: decision `2026-10-19-tracked-pointer-rule`.

## Behavior

**Form.** `wb preview enroll [<target> | --dir <path>]` shows what would be written and a digest, and writes nothing. [call] `wb enroll [<target> | --dir <path>]` is owner-run: standard input and output must be terminals, the whole list and the digest are shown, and the owner types the first 12 characters of the digest. [agreed] Typed-ahead input is discarded, and anything else writes nothing; the 12 characters and the discarding follow `acknowledge`. [call]

**Level.** The key `wb enroll` is class `governs` and offers `block` only, so there is no `ask` or `none` and no run without a terminal, as for `wb rerender`. [call] The reason is its own, not `wb rerender`'s: the command writes the trust state that every other command relies on, the owner's typed digest is its only confirmation, and a level at which an agent could run it would drop that confirmation (`command-permissions.md`, "The key `wb enroll`"). [call]

**Registration.** The key is added to the levels registry with `wb preview enroll` as its preview; the harness's deny rule for owner-run commands names it; the command gate's key words include it; and the command tables of `development.md`, `installer-interface.md` and `command-permissions.md` list it. [call] Those tables, and the usage text of the command line, spell every row in the long form `python3 -m workbench <command>`, as they do for the other commands; the launcher form is the one an owner or a script uses (`installer-interface.md`, the launcher rule). [call]

**What it reads.** In the clone: the committed manifest, every file the manifest records, the names under `.workbench/` outside `local/` (to find a file the manifest does not record), and the top directory with its `.git` and manifest entries (for the target checks). In the guarded store: the project's `baselines` and `seen` entries. [call] It runs no git and fetches nothing. [agreed]

**What it checks.** Before it shows anything:

1. The target is resolved and classified as every command does it (`installer-interface.md`, "Refused places" and the states table): a refused place is refused, and the target must be an existing project, a real directory with its own `.git` and a regular-file `.workbench/manifest.json`. Anything else is a refusal. [call]
2. The project has neither baselines nor a `seen` record for its id in the store. This is the one command that requires the project to be unknown on this machine; every other command requires it to be known. [agreed] If both entries exist, the project is known and the command refuses and names `acknowledge`. [agreed] If exactly one exists, or an entry is malformed, the command refuses, names the entry and writes nothing. [call] Both entries are created only after every check has passed. [call] If the project's folder in the store holds any other entry of an earlier project of the same identity (a `pins`, `rendering` or `plan-approvals` entry; a test lists every entry the installer writes in a project's folder, so that a new kind is weighed here), the command refuses and says to remove the folder by hand: a pin binds a path and the hash of a helper, and the owner's earlier confirmation of it is not a confirmation of this clone. [call]
3. The manifest reads through the same strict reader the other commands use (`installed.read`), and every path it records passes the project's path rules (`repository-boundary.md`, `module-contract.md`). [call] Each recorded path lies where its owner may write: a module's own namespace under `.workbench/<package>/<module>/`, a path in that module's declared `writes`, a file the base supplies, `.workbench/.gitignore` or the manifest; never under `.workbench/local/`. An entry outside those places, a class other than the ones the installer writes, or a block whose slot its module does not declare is a refusal that names the entry, and nothing is written. [call] The declaration used for the `writes` and the slots is the module's own `module.json` as copied into the clone under `.workbench/<package>/<module>/`, whose hash the manifest records and the check above compares; the command takes no package. It is the clone's own file, so this is a consistency check on the manifest and not a trust anchor: the anchor for the bytes of the helpers is the package verification of `upgrade`. [call] The files the base supplies are those of the running workbench's base, not of the base the project was installed from, so a seeded path that an older base supplied and this one no longer does is refused until the project is upgraded. [call] Every recorded path that exists is a regular file, never a link, a directory or another kind. [call]
4. Every file the manifest records as module-owned equals the hash the manifest records for it. A file that differs or is missing is a refusal that names its path. [agreed] Every recorded file is read twice, once to judge it and once for its baseline, and every entry of the path (a module-owned file, a seeded file, each of its slot blocks) is judged again on the second read: if any state or hash differs, or the file was removed or put back in between, the command refuses and names the file. [call]
5. A file the manifest records as seeded, such as `AGENTS.md` or a `docs/*/README.md`, is the owner's to edit, so its bytes may differ from the hash the manifest records. It does not refuse. [agreed] The baseline is taken from the bytes now in the clone, and the preview lists the file as "differs from the manifest (seeded, yours)". [agreed] A seeded file that is missing is listed and given no baseline. [call]
6. A file under `.workbench/` outside `local/` that the manifest does not record is neither refused nor baselined. [agreed] This repository tracks one such file besides the review records of its plans and specs, which the review engine keeps under its module's namespace and the project commits, so a refusal would make it, and any project that commits a review, unenrollable (decision `2026-11-15-enroll-baselines-only-what-the-manifest-records`). [agreed] The preview says how many there are and under which directories, and says that `acknowledge` lists them next. [call] A file deeper than `.workbench/<package>/<module>/` is counted under that module directory, so that the review records of a project, each in a directory of its own, are one group and not several hundred lines; a file elsewhere is counted under its own directory; a group is listed path by path only if it holds ten or fewer. [call] A link, a directory in place of a file, or another kind of file in that scope is a refusal that names it. [call]
7. A slot block the manifest records (class `slot block`, with the hash of its block text and the path of the file that holds it, such as a policy block in `AGENTS.md`) lives inside a seeded file. The command finds the block in the clone's file as the installer's block scanner does (`blocks.scan`) and compares the SHA-256 of its exact bytes, from the first byte of its BEGIN marker line through the last byte of its END marker line with their line endings, with the manifest's hash. That is the byte range `install` hashes (`installplan.py`, where the block is built from the two marker lines and the module's text). A block that matches is not listed. A block that differs or is missing does not refuse, because its file is the owner's to edit; the preview lists it as "block differs from the manifest (seeded file, yours)" with the file and the block's name. [call] `upgrade` then shows such a block as a conflict ("edited by the project") and does not overwrite it. [call] A slot block must lie in a file that the manifest also records as seeded; a block entry for any other path is a refusal. [call] A seeded file whose slot markers cannot be read (a duplicated or unmatched marker) is a refusal that names it, because its blocks cannot be told from its text. [call] The baseline of the containing file is the hash of the whole file as it is in the clone, as `install` records the bytes written, so a file with blocks gets one baseline whatever its blocks say. [call]

**What it writes.** In the guarded store, in one call that stages both entries and then puts them in place one after the other (so each entry is whole or absent), for the project's id: `projects/<id>/baselines` (the hash of every file the manifest records, as checked above, and of `.workbench/manifest.json` itself, as `install` records it) and `projects/<id>/seen` (the clone's resolved absolute path). [agreed] It writes nothing in the project. [agreed] It writes nothing else, and in particular no level log: the key offers `block` only and the command runs only at a terminal, and the level log records runs of the levels `ask` and `none`, so there is none to write, as for `wb rerender`. [call] Both entries are staged before either is put in place, and they are read back and checked as the other commands read them. [call] Once the entries are written and read back the command has done what it was asked, whatever happens to its closing line (a closed pipe, an interrupt); an interrupt after the write has begun says "interrupted after the entries were written" and not that nothing was written. [call] If a write fails, the command says so and names what the store holds; a store with only one of the two entries is a state the command itself refuses (check 2), and the message says which entry to remove by hand and to run the command again. [call]

**Pins and approvals.** The command writes no pin and reads no approval record. [agreed] A pin is created by the next step, `wb upgrade --package <directory>` (for this repository `packages/workbench`, which the clone holds): `upgrade` verifies the package against the approvals on the machine, compares what is installed with what the package would write, and creates a pin, at the bytes it confirms, for each helper that has none (`upgradeplan._pins`). [agreed] For a helper left as it is, the pin is made only if its acknowledged bytes equal the manifest's hash; for a helper whose bytes in the package differ from the manifest's, the file in the clone is replaced by the package's bytes and pinned at them, so a helper planted in the clone with its manifest hash changed to match is overwritten. [call] `upgrade` also needs every module it selects approved on the machine (`gate.check_selection`): the shipped records cover this repository's own modules, and a third-party module needs the owner's `approve` first. [call] Until then no helper of the clone runs through the launcher, and `wb check` reports each as not pinned. [call] The reason is in the decision: the manifest's hashes, and an approval looked up by them, do not bind the helper bytes, so an approval check here would only look like one. [agreed]

**What it leaves to other commands.** After it, `wb check`, `wb doctor`, `acknowledge`, `upgrade` and `add` run on the clone without the "treated as new" refusal. [agreed] The files under `.workbench/` that the manifest does not record show to `acknowledge` as added, and the owner acknowledges them; `upgrade` needs the clone to hold no difference, so the order on a new machine is `enroll`, `acknowledge`, `upgrade` with a package, then `attach`. [agreed] The helpers are pinned by `upgrade` with a package, as above, and the harness is attached by `attach`, which still needs each package approved on this machine. [agreed] `acknowledge` refuses a list of more than 500 paths (`MAX_LISTED` in `workbench/acknowledge.py`), so a clone with more unrecorded files than that cannot pass that step until the limit is settled; it is a limit of `acknowledge`, not of this command. [call]

**The preview** shows: the project id and the path that would be recorded; each file with its hash and its class, one by one up to 400 and counted beyond that (the digest covers all of them); each seeded file that differs; the paths outside `.workbench/` that the base does not supply and that rest only on a module's own declaration of what it writes, under their own heading, every one of them listed and a module-owned file whatever its path, because nothing else checks them and the heading is the owner's only notice; the summary of unrecorded files under `.workbench/` (check 6), by directory up to 400 and counted beyond that; and the digest. [call] The digest covers the list, as `acknowledge`'s does, and the command re-reads the clone after the owner types it and refuses if the digest differs. [call]

**What stays open.** Whether the preview says, as a last line, that `attach` still needs each package approved on this machine. [open]

## Acceptance criteria

1. On a fresh clone with a scratch `HOME` and the commit of the day, after the first run of the workbench has written the guarded store and the launcher as every command's first run does (`installer-interface.md`), `preview enroll` lists the baselines and the `seen` path and writes no entry for the project in the store and nothing in the project. The same read, run on a copy of this repository's own tracked files, gives no refusal.
2. `enroll` run from a terminal with the typed digest writes exactly the two store entries (the baselines and the first-seen record) and nothing in the project, and no pin and no level log; afterwards `wb check`, `wb doctor` and `preview acknowledge` run without the "treated as new" refusal, and `preview acknowledge` lists no difference for the manifest or for any path the manifest records, and lists as added exactly the unrecorded files under `.workbench/`.
3. It refuses, naming the entry, a manifest entry outside the places its owner may write (including one under `.workbench/local/`), an unknown class, and a block whose slot the module does not declare. It refuses, naming the path, a module-owned file whose hash differs from the manifest, a missing module-owned file, a link, a directory in place of a file, a link or a directory in place of an unrecorded file under `.workbench/`, a refused place, and a directory that is not an existing project.
4. It does not refuse a seeded file that differs; the preview lists it and the baseline is the bytes in the clone. It does not refuse and does not baseline a regular file under `.workbench/` that the manifest does not record; the preview counts such files by directory.
5. After `enroll` and `acknowledge`, `wb preview upgrade --package packages/workbench` runs on the clone without the "treated as new" refusal and lists a pin to create for each helper of each module that the package still declares, at the bytes the package would write (a module the package no longer declares is left in place and gets none); `wb upgrade` with that digest creates them, and `wb check` then reports no helper as not pinned.
6. It refuses a project the machine already knows and names `acknowledge`, and refuses, naming the entry and writing nothing, a project with only one of the two entries or a malformed one.
6a. A slot block that differs from the manifest does not refuse; the preview lists it with its file and name, and the baseline of its file is the hash of the whole file in the clone.
7. It refuses without two terminals, refuses a wrong or typed-ahead digest, and refuses when the clone changed between the preview and the answer.
8. `wb settings` prints the key `wb enroll` with `offers=` empty, and the command refuses to run with the key changed to any other level.
9. A security review of the built command finds no way for the files of a clone to be accepted without the owner's digest, no pin written or approval record read by `enroll`, and no write in the store outside `projects/<id>/`.
10. `INSTALL.md` describes the command and the steps that follow it, and the owner has run them on a second machine.

## As built

Built by the plan `2026-11-15-enroll-a-clone` (increments B to F, committed 2026-11-15). The spec stays `Draft` until the owner says it reads `Current`, after the owner's run on a second machine (criterion 10).

- **Commands.** `wb preview enroll` and the owner-run `wb enroll` (`workbench/enroll.py`, routed in `workbench/cli.py`); the read is `workbench/enrollplan.py` (`examine`, `render`, the plan and its digest). The key `wb enroll` (class governs, `block` only) and its derived preview key are in `workbench/levels.py`.
- **Tests.** `tests/test_enroll_plan.py`, `tests/test_enroll_preview.py` and `tests/test_enroll.py` (101 tests), written first and mutation-tested (30 mutants of the read, 16 of the command, none surviving), and the lists in `test_levels`, `test_permissions`, `test_owner_run_arguments` and `test_rendering`. Criteria 1 to 9 are covered by them; criterion 5 (the pins follow from `upgrade` with the package) by two tests that install a project in a store that does not know it, enroll it, acknowledge it and run the preview of `upgrade`, one with a helper planted in the clone.
- **A run on a real clone.** On 2026-11-15, on a fresh `git clone` of this repository at `7d70877` with a scratch `HOME`, driven in process with a fake terminal: the preview listed 73 baselines, 5 paths outside `.workbench/` resting on a declaration and 461 unrecorded files (one and 460 review records); `enroll` wrote the two entries; `acknowledge` listed 461 paths and recorded them; the preview of `upgrade` with `packages/workbench` listed 14 pins to create and `77 skip, 1 conflict; 0 file writes`; `upgrade` created them; `check` and `doctor` then reported no problems; the preview of `attach` listed 26 files. Not run: the same by hand at a real terminal on a second machine, and `attach` itself.
- **Reviews.** The spec, in four rounds by a second model (nine findings applied); the plan, in three (six applied); a reviewer agent for each increment; and a security review with an independent second look at its fixes (no Critical, High or Medium finding in either: the first review had four Low and four informational findings, five fixed and three recorded in the plan's Result, and the second look had four Low findings, all fixed). The second round of fixes has no look of its own.
- **Known limits.**
  - `acknowledge` refuses a list of more than 500 paths (`MAX_LISTED`), and this repository is about 39 files below that bound with 461 unrecorded files, each review adding 6 to 13. It is a limit of `acknowledge`, filed on the owner's list.
  - The two entries are staged together and put in place one after the other; a failure between the two leaves the baselines only, which the command names and refuses to enroll over until the owner removes it by hand.
  - The typed answer is stripped of surrounding white space, and a pseudo-terminal passes the terminal test, as for `wb rerender`; the narrow race between the second read and the write is the same as `acknowledge`'s.
  - The check that a path lies where its module may write reads the clone's own `module.json`, and `_same_as_judged` uses the private function `installed._entry`; a change to `installed.read` must be followed there.
  - A clone with a file name that the path rules refuse under `.workbench/` cannot be enrolled, and a fork that shares the seed of a known project is refused as known.
