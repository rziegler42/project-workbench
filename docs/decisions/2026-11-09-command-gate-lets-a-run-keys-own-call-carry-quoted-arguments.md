# The command gate lets the own call of a relaxed `wb run` key carry single-quoted arguments

Status: Accepted by Robert Ziegler <25854477+rziegler42@users.noreply.github.com> on 2026-11-09

## Context

`2026-10-26-ask-level-command-gate` has the command gate stop a Bash command that names a relaxed command unless it is exactly the simple command that the `ask` rule matches, so that the harness's rule, which prompts the owner, is the only way the command can run. `2026-10-27-command-gate-literal-arguments` freed a literal `wb run <name> <arguments>` call for a single-word key and named the keys of the form `wb run <command> <argument>` as not exempted; `2026-10-28-gate-reads-module-arguments` freed the first plain argument of the key's own command for those keys (so a preview is not searched for the key's words). Neither changed what the key's own call must look like to be "the simple command the `ask` rule matches".

In `workbench/command_gate.py`, `forms(key, store_bin)` gives that form for a key of the form `wb run <command> <argument>`: `wb run <command> <argument>` followed by plain tokens of `[A-Za-z0-9._/:=-]+`, each after one space. A token has no space and no quote.

`2026-11-03-delegated-for-an-action-key-and-named-risk-profiles` offers `delegated` for an action key that a module describes, and `2026-11-08-action-review-cutover-for-commit` made `wb run safe-git commit` such a key and renders its `delegated` level as an `ask` rule, which the gate counts as relaxed. A commit always carries free text: `--subject 'some words'`, and for a plan increment `--trailer 'Plan: <stem>#<label>'`. Such a call is not the form above, so the gate refuses it: on 2026-11-09, with the key at `delegated`, `wb run safe-git commit --expected-head <hash> --state-digest <digest> --subject '<words>' --trailer 'Plan: <stem>#F' -- <path>` was refused with `the command names safe-git commit, which the owner has set to ask or none here, and is not exactly the simple command the ask rule matches (rule: names)` before anything ran. The key cannot be used while the gate reads it so. The engine that reviews the command is not the cause: its parser accepts single-quoted words with `#` in them.

The harness's rendered rule is wider than the gate's form. For this key it is `Bash(wb run safe-git commit *)` (with the `--provides` and guarded-store spellings), a prefix with a wildcard. The gate's purpose is that the rule can fire, so that the owner is asked; the question this record settles is whether it fires for a call with a single-quoted argument. It does (see Evidence).

## Decision

Proposed. Nothing here is built; Increment C of `2026-11-09-command-gate-quoted-arguments-for-a-run-key` builds it once the owner accepts this record.

1. **The own call of a relaxed key `wb run <command> <argument>` may carry single-quoted arguments.** For such a key, the exact form that `forms` gives becomes `(wb|<the guarded store's bin/wb>) run <command> <argument>( <argument-word>)*`, matched in full (`fullmatch`, so no trailing newline) on the raw text, where `<argument-word>` is a plain token (`[A-Za-z0-9._/:=@,+-]+`, the gate's `_RUN_PLAIN`) or one single-quoted string. **A single-quoted string holds no newline and no carriage return and no quote**: bash reads it literally, and the probe below covered a string with spaces and a `#` and no newline. This is narrower than the literal form of `2026-10-27-command-gate-literal-arguments`, which allows a newline in quotes; a multi-line argument for these keys needs its own probe and its own record.
2. **Decided per key and never an early return for the others.** The loop of the gate judges every relaxed key on its own. A call that matches the widened form of one key is still searched for the words of the other relaxed keys, with the exemptions the accepted decisions give, so a commit whose quoted subject holds the words of `wb run review-engine extend` is still refused, and one that holds `approve-plan` passes as it does today (decision 4 of `2026-11-02-command-gate-reads-gaps-and-data-positions`).
3. **Nothing else changes.** A double-quoted, escaped, substituted or globbed argument, a `$`, a backtick, `;`, `&&`, `|`, a redirection, a newline outside quotes, an unclosed quote, a trailing newline, a path to `wb` that is neither `wb` nor the guarded store's own `bin/wb`, a `--provides` spelling, the single-word keys, `approve-plan`, the `gap`, `size-limit` and `dollar-quote-limit` rules, the levels, the rendering, the log and the launcher are judged as the accepted decisions say.

This refines the accepted decisions' statement that the `wb run <command> <argument>` keys are not exempted (point 1 of `2026-10-27-command-gate-literal-arguments`, refined once by `2026-10-28-gate-reads-module-arguments`). It does not edit those records.

## Alternatives considered

- **Leave the gate and have the owner commit by hand.** Nothing to build, and the gate stays as strict as it is. Rejected: it makes `delegated` for a commit unusable, which is the cutover the cutover plan exists to try; and the same limit would meet any key of this form that takes free text.
- **Render a narrower rule for the commit key, so the gate's plain form is the rule.** Rejected: the harness's rule is a prefix with a wildcard and cannot say "plain tokens"; and the subject is free text, so the call cannot be plain.
- **Give the agent a wrapper command that takes the subject and trailer from a file, so no quote is needed.** Rejected for now: it is a new command in another module, the text of the file would be a new thing to review, and it moves the free text rather than removing it. It stays open (see the plan's deferred work).
- **Allow every `wb run` call for these keys, whatever the name or the arguments.** Rejected for the reasons of `2026-10-28-gate-reads-module-arguments`: it would free a pin of the same helper under another name and every argument form the gate cannot read.
- **Accept the literal form of the 2026-10-27 record exactly, newline in quotes included.** Rejected until it is probed: the harness may treat a newline inside a quoted argument as a command separator when it matches a rule, and the gate's purpose is that the rule fires.

## Consequences

- Good: the call that a commit needs passes the gate, and the harness's rule is still what stops it: the owner is asked, or the hook that may answer the request does. The cutover trial of `wb run safe-git commit` at `delegated` can be tried.
- Good: the change is one form in `forms()`, for the keys of one shape; every other key and rule is as before, and the tests of the plan pin that.
- Bad: a subject with an apostrophe cannot be single-quoted, so the agent rewords it; a multi-line `--body` cannot be passed (no newline in quotes), so a body is one line.
- Bad: a quoted argument that holds the words of another relaxed key of this shape is still refused (a commit subject that mentions `review-engine extend`), as before.
- Bad: the gate still reads text. A call that builds a relaxed key's words at run time is the limit of the earlier decisions, and this record does not move it. A rule that did not fire for a quoted argument would make the widened form let a call through that nothing prompts for; the probe shows it fires for the commit key's rule in the two modes the owner uses, and the record stands only on that.
- Bad: the commit key's own call is trusted text between the quotes. The words in them reach the helper as an argument, which the helper and the engine read; the gate does not.

## Evidence

- The refusal: 2026-11-09, project commit `af1d7ab`, the command gate of this project, a Bash call of the form in Context with the key `wb run safe-git commit` at `delegated`; the gate's answer is quoted in Context. The form `forms(key, store_bin)` was read in `workbench/command_gate.py` at that commit: `"%s%s%s(?: %s)*" % (head, middle, tail, _TOKEN)` with `_TOKEN = r"[A-Za-z0-9._/:=-]+"`.
- The rule as the installer renders it: `python3 -I -B` importing `workbench.rendering` of this project's tree and calling `plan` with a table that sets `wb run safe-git commit` to `delegated` and `wb run review-engine amend` to `ask`: the `ask` patterns are `wb run safe-git commit`, `wb run safe-git commit *`, `wb run --provides * safe-git commit` and `wb run --provides * safe-git commit *` (the same four for the other key), spelled `Bash(<pattern>)` with `wb` and with the guarded store's `bin/wb`. Increment A of the plan, commit `88a07cc`.
- The probe: 2026-11-09, Claude Code 2.1.319 (as `claude --version` prints), a throwaway project with the eight `ask` rules of the commit key, a fake `wb` that only records its arguments, the command gate replaced by a recording hook that allows the call and a recording `PermissionRequest` hook. The owner typed `Run this exact Bash command and nothing else, do not change it: wb run safe-git commit --expected-head 0123456789abcdef0123456789abcdef01234567 --subject 'A probe subject with spaces' --trailer 'Plan: probe-stem#F' -- a.txt`. With auto mode on, the harness showed a prompt saying "Ask rule Bash(wb run safe-git commit *) overrides auto mode for this command"; with auto mode off, "Permission rule Bash(wb run safe-git commit *) requires confirmation for this command". The log has a `PreToolUse` and a `PermissionRequest` entry for each, in modes `auto` and `default`, with the whole command intact; the fake `wb` never ran. Not tested: the real gate, a newline in a quoted argument, a key that offers `ask`, other versions.
- The conclusion: for the commit key in the two modes the owner uses, the harness's rule fires on a call with a single-quoted argument that holds spaces and a `#`, so widening the gate's form to such a call does not let a call through unprompted.
