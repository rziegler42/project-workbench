# Clone enrollment

Status: Draft. Written on 2026-11-15 from a conversation with the owner, for the roadmap candidate `workbench-v1#enrol-a-clone`. It describes a command that is not built. It is `Current` only when the owner says so, after it is built.

Each statement carries one of three marks, so that the owner can see what is theirs:

- **[agreed]** The owner said it, or approved it in a playback on 2026-11-15. It is the working position and it can still change.
- **[call]** The assistant's choice, made so the design is complete. The owner has not decided it.
- **[open]** Not decided. The builder asks the owner, or the owner decides when approving.

Terms are defined in `terms.md`. The commands this one sits beside are in `installer-interface.md`, the store and the baselines in `trust-and-approval.md` ("Acknowledgement"), and the per-clone files in `repository-boundary.md`.

## Scope

A command that makes a clone of an already installed project known on a machine that has never held it, so that the checks, `attach`, `upgrade`, `add` and `acknowledge` work on that clone. [agreed] The project's helpers are pinned afterwards by `upgrade` with a package, not by this command (decision `2026-11-15-enroll-writes-no-pins-and-leaves-them-to-upgrade-from-a-package`). [agreed]

The commands are `wb enroll` and a read-only `wb preview enroll`. [call] They are run through the `wb` launcher, never as `python3 -m workbench`, which would put the clone's own directory first on the module search path (`installer-interface.md`, the launcher rule). [call] The launcher is written by the first run of the workbench in the clone, which is the first step of the setup page `INSTALL.md`; `enroll` is a later step. [call]

## Non-goals

- Moving or copying a project to another path on one machine, or any use of an earlier project's baselines or pins (`repository-boundary.md` says such a project is treated as new). [agreed]
- Comparing the clone with the first machine's store, or with a remote. The basis of trust is the committed manifest's hashes and the digest the owner confirms. [agreed]
- Writing an approval or a pin, reading an approval record, fetching a package, or attaching a harness. The pins come from `upgrade` with a package, which verifies the package against the approvals and the bytes it would write; `approve` and `attach` stay the existing commands, run before or after as each needs. [agreed]
- Copying the owner's personal settings, review profiles or bridge endpoints. They are per machine, and `INSTALL.md` says so. [call]
- Any change to what a baseline or a pin means, or to the file formats of the store. [agreed]
- A way to enroll a project that was never installed. `install` and `adopt` do that. [call]

## Assumptions and constraints

- Every command that acts on an installed project first requires that the guarded store hold `projects/<id>/baselines` and a `seen` record equal to the clone's resolved path; otherwise the project is "treated as new here" and the command refuses. `enroll` is the one exception: it is the command that makes the project known. Source: `acknowledgement.check_known`, called by `attach`, `upgrade` and `acknowledge`; `trust-and-approval.md`, "What a command checks before it acts on a project".
- Today only `install` and `adopt` create the baselines, the `seen` record and the pins (`installplan.py`, the `store_writes` and `pinplan` steps; `upgrade` and `acknowledge` rewrite the baselines of a project already known, and `upgrade` creates the pin of a helper that has none, `upgradeplan._pins`), and `adopt` refuses an existing project ("use wb upgrade or wb add"). So a clone of an installed project cannot be made known by any command. Evidence, 2026-11-15, at commit `459dde9`: on a fresh clone with a scratch `HOME`, `preview attach` refused with "this machine holds no acknowledgement baselines for the project; it is treated as new here"; on the owner's second machine, `preview acknowledge` refused the same way and `preview adopt --dir . --package packages/workbench --select <the ten modules of the manifest>` refused with "the target is an existing project; use wb upgrade or wb add".
- The project's identity is the id derived from the manifest's seed (`manifest.project_id`), so the clone has the same id on every machine. The `seen` record holds an absolute path, so it differs between machines. Source: `acknowledgement.read_seen`, `check_known`.
- The baselines file is strict JSON, `{"baselines": {<path relative to the project root>: <sha256 hex of the bytes>}, "format": 1}`. Source: `trust-and-approval.md`, "Baselines file".
- An owner-run command is terminal-only unless its key offers `ask` or `none`; `wb rerender` offers `block` only. Source: `levels.py`, decision `2026-10-27-rerender-is-terminal-only`.
- A tracked document does not cite an untracked file. Source: decision `2026-10-19-tracked-pointer-rule`.

## Behavior

**Form.** `wb preview enroll [<target> | --dir <path>]` shows what would be written and a digest, and writes nothing. [call] `wb enroll [<target> | --dir <path>]` is owner-run: standard input and output must be terminals, the whole list and the digest are shown, and the owner types the first 12 characters of the digest. [agreed] Typed-ahead input is discarded, and anything else writes nothing; the 12 characters and the discarding follow `acknowledge`. [call]

**Level.** The key `wb enroll` is class `governs` and offers `block` only, so there is no `ask` or `none` and no run without a terminal, as for `wb rerender`. [call]

**Registration.** The key is added to the levels registry with `wb preview enroll` as its preview; the harness's deny rule for owner-run commands names it; the command gate's key words include it; and the command tables of `development.md`, `installer-interface.md` and `command-permissions.md` list it. [call]

**What it reads.** In the clone: the committed manifest, every file the manifest records, the names under `.workbench/` outside `local/` (to find a file the manifest does not record), and the top directory with its `.git` and manifest entries (for the target checks). In the guarded store: the project's `baselines` and `seen` entries. [call] It runs no git and fetches nothing. [agreed]

**What it checks.** Before it shows anything:

1. The target is resolved and classified as every command does it (`installer-interface.md`, "Refused places" and the states table): a refused place is refused, and the target must be an existing project, a real directory with its own `.git` and a regular-file `.workbench/manifest.json`. Anything else is a refusal. [call]
2. The project has neither baselines nor a `seen` record for its id in the store. This is the one command that requires the project to be unknown on this machine; every other command requires it to be known. [agreed] If both entries exist, the project is known and the command refuses and names `acknowledge`. [agreed] If exactly one exists, or an entry is malformed, the command refuses, names the entry and writes nothing. [call] Both entries are created only after every check has passed. [call]
3. The manifest reads through the same strict reader the other commands use (`installed.read`), and every path it records passes the project's path rules (`repository-boundary.md`, `module-contract.md`). [call] Each recorded path lies where its owner may write: a module's own namespace under `.workbench/<package>/<module>/`, a path in that module's declared `writes`, a file the base supplies, `.workbench/.gitignore` or the manifest; never under `.workbench/local/`. An entry outside those places, a class other than the ones the installer writes, or a block whose slot its module does not declare is a refusal that names the entry, and nothing is written. [call] The declaration used for the `writes` and the slots is the module's own `module.json` as copied into the clone under `.workbench/<package>/<module>/`, whose hash the manifest records and the check above compares; the command takes no package. It is the clone's own file, so this is a consistency check on the manifest and not a trust anchor: the anchor for the bytes of the helpers is the package verification of `upgrade`. [call] Every recorded path that exists is a regular file, never a link, a directory or another kind. [call]
4. Every file the manifest records as module-owned equals the hash the manifest records for it. A file that differs or is missing is a refusal that names its path. [agreed]
5. A file the manifest records as seeded, such as `AGENTS.md` or a `docs/*/README.md`, is the owner's to edit, so its bytes may differ from the hash the manifest records. It does not refuse. [agreed] The baseline is taken from the bytes now in the clone, and the preview lists the file as "differs from the manifest (seeded, yours)". [agreed] A seeded file that is missing is listed and given no baseline. [call]
6. A file under `.workbench/` outside `local/` that the manifest does not record is neither refused nor baselined. [agreed] This repository tracks one such file besides the review records of its plans and specs, which the review engine keeps under its module's namespace and the project commits, so a refusal would make it, and any project that commits a review, unenrollable (decision `2026-11-15-enroll-baselines-only-what-the-manifest-records`). [agreed] The preview says how many there are and under which directories, a count for each directory and every path where a directory holds ten or fewer, and says that `acknowledge` lists them next. [call] A link, a directory in place of a file, or another kind of file in that scope is a refusal that names it. [call]
7. A slot block the manifest records (class `slot block`, with the hash of its block text and the path of the file that holds it, such as a policy block in `AGENTS.md`) lives inside a seeded file. The command finds the block in the clone's file as the installer's block scanner does (`blocks.scan`) and compares the SHA-256 of its exact bytes, from the first byte of its BEGIN marker line through the last byte of its END marker line with their line endings, with the manifest's hash. That is the byte range `install` hashes (`installplan.py`, where the block is built from the two marker lines and the module's text). A block that matches is not listed. A block that differs or is missing does not refuse, because its file is the owner's to edit; the preview lists it as "block differs from the manifest (seeded file, yours)" with the file and the block's name. [call] `upgrade` then shows such a block as a conflict ("edited by the project") and does not overwrite it. [call] The baseline of the containing file is the hash of the whole file as it is in the clone, as `install` records the bytes written, so a file with blocks gets one baseline whatever its blocks say. [call]

**What it writes.** In the guarded store, in one atomic step, for the project's id: `projects/<id>/baselines` (the hash of every file the manifest records, as checked above, and of `.workbench/manifest.json` itself, as `install` records it) and `projects/<id>/seen` (the clone's resolved absolute path). [agreed] It writes nothing in the project. [agreed] Besides the project's store directory it writes only the level log, with its attempt before the writes and its outcome after, as the other owner-run commands do. [call]

**Pins and approvals.** The command writes no pin and reads no approval record. [agreed] A pin is created by the next step, `wb upgrade --package <directory>` (for this repository `packages/workbench`, which the clone holds): `upgrade` verifies the package against the approvals on the machine, compares what is installed with what the package would write, and creates a pin, at the bytes it confirms, for each helper that has none (`upgradeplan._pins`). [agreed] For a helper left as it is, the pin is made only if its acknowledged bytes equal the manifest's hash; for a helper whose bytes in the package differ from the manifest's, the file in the clone is replaced by the package's bytes and pinned at them, so a helper planted in the clone with its manifest hash changed to match is overwritten. [call] `upgrade` also needs every module it selects approved on the machine (`gate.check_selection`): the shipped records cover this repository's own modules, and a third-party module needs the owner's `approve` first. [call] Until then no helper of the clone runs through the launcher, and `wb check` reports each as not pinned. [call] The reason is in the decision: the manifest's hashes, and an approval looked up by them, do not bind the helper bytes, so an approval check here would only look like one. [agreed]

**What it leaves to other commands.** After it, `wb check`, `wb doctor`, `acknowledge`, `upgrade` and `add` run on the clone without the "treated as new" refusal. [agreed] The files under `.workbench/` that the manifest does not record show to `acknowledge` as added, and the owner acknowledges them; `upgrade` needs the clone to hold no difference, so the order on a new machine is `enroll`, `acknowledge`, `upgrade` with a package, then `attach`. [agreed] The helpers are pinned by `upgrade` with a package, as above, and the harness is attached by `attach`, which still needs each package approved on this machine. [agreed] `acknowledge` refuses a list of more than 500 paths (`MAX_LISTED` in `workbench/acknowledge.py`), so a clone with more unrecorded files than that cannot pass that step until the limit is settled; it is a limit of `acknowledge`, not of this command. [call]

**The preview** shows: the project id and the path that would be recorded; each file with its hash and its class; each seeded file that differs; the summary of unrecorded files under `.workbench/` (check 6); and the digest. The digest covers the list, as `acknowledge`'s does, and the command re-reads the clone after the owner types it and refuses if the digest differs. [call]

**What stays open.** Whether the preview says, as a last line, that `attach` still needs each package approved on this machine. [open]

## Acceptance criteria

1. On a fresh clone with a scratch `HOME` and the commit of the day, after the first run of the workbench has written the guarded store and the launcher as every command's first run does (`installer-interface.md`), `preview enroll` lists the baselines and the `seen` path and writes no entry for the project in the store and nothing in the project. The same read, run on a copy of this repository's own tracked files, gives no refusal.
2. `enroll` run from a terminal with the typed digest writes exactly the two store entries (the baselines and the first-seen record), the level log and nothing in the project, and no pin; afterwards `wb check`, `wb doctor` and `preview acknowledge` run without the "treated as new" refusal, and `preview acknowledge` lists no difference for the manifest or for any path the manifest records, and lists as added exactly the unrecorded files under `.workbench/`.
3. It refuses, naming the entry, a manifest entry outside the places its owner may write (including one under `.workbench/local/`), an unknown class, and a block whose slot the module does not declare. It refuses, naming the path, a module-owned file whose hash differs from the manifest, a missing module-owned file, a link, a directory in place of a file, a link or a directory in place of an unrecorded file under `.workbench/`, a refused place, and a directory that is not an existing project.
4. It does not refuse a seeded file that differs; the preview lists it and the baseline is the bytes in the clone. It does not refuse and does not baseline a regular file under `.workbench/` that the manifest does not record; the preview counts such files by directory.
5. After `enroll` and `acknowledge`, `wb preview upgrade --package packages/workbench` runs on the clone without the "treated as new" refusal and lists a pin to create for each helper of each module that the package still declares, at the bytes the package would write (a module the package no longer declares is left in place and gets none); `wb upgrade` with that digest creates them, and `wb check` then reports no helper as not pinned.
6. It refuses a project the machine already knows and names `acknowledge`, and refuses, naming the entry and writing nothing, a project with only one of the two entries or a malformed one.
6a. A slot block that differs from the manifest does not refuse; the preview lists it with its file and name, and the baseline of its file is the hash of the whole file in the clone.
7. It refuses without two terminals, refuses a wrong or typed-ahead digest, and refuses when the clone changed between the preview and the answer.
8. `wb settings` prints the key `wb enroll` with `offers=` empty, and the command refuses to run with the key changed to any other level.
9. A security review of the built command finds no way for the files of a clone to be accepted without the owner's digest, no pin written or approval record read by `enroll`, and no write in the store outside `projects/<id>/` and the level log.
10. `INSTALL.md` describes the command and the steps that follow it, and the owner has run them on a second machine.
